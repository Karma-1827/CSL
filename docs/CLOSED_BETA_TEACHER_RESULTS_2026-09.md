- 回覆來源：`MPTS 封閉測試回報－老師 (回覆).xlsx`

- 分析日期：2026-09-05
- 分析範圍：工作表「表單回覆 1」第 2 至第 5 列

本文件不得被當成「系統已驗收通過」的證明。第一輪樣本量小，且跨角色流程的有效測試不足。

## 3. 確認缺陷

### P1-01：超大口語能力證明上傳後，頁面疑似卡住

#### 回報內容

測試者上傳約 40 MB 的 PDF，按下「重新送審」後頁面卡住，沒有立即顯示「檔案不可超過 1 MB」。使用上一頁才回到原畫面。

#### 判定

這是需要修正的問題，不應歸因為使用者操作錯誤。系統即使收到違規檔案，也應快速拒絕並提供可理解的訊息。

此問題除了使用體驗，也涉及大量檔案上傳占用網路、Nginx 及應用程式資源的風險。

#### 建議處理

1. 使用者選取檔案後，在瀏覽器端立即檢查容量。
2. 超過 1 MB 時阻止送出，顯示雙語錯誤。
3. 保留 Django 後端的 1 MB 驗證，不能只依賴瀏覽器端。
4. 確認正式 VM 的 Nginx `client_max_body_size` 設定已生效。
5. 為 HTTP 413 提供清楚的雙語錯誤畫面或導回原頁顯示訊息。
6. 上傳失敗時，不得覆蓋或刪除原本已核准的文件。

#### 驗收方式

分別測試以下檔案：

- 小於 1 MB 的合法 PDF。
- 略大於 1 MB 的合法 PDF。
- 12 MB PDF。
- 40 MB PDF。
- 副檔名正確但內容不是 PDF 的檔案。

超過限制或內容不合法時，系統應快速拒絕、顯示原因、保留原有文件，且不得留下新的資料庫紀錄或伺服器檔案。

## 4. 介面與操作改善

以下項目為合理的使用者回饋，但不等同於功能故障。修改前應先確認是否符合全站一致性。

### P1-02：錯誤提示不夠明顯，密碼規則不清楚

不同測試者重複反映：

- 「此欄位為必填欄位」與紅框不夠明顯。
- 一般暗紅色與錯誤紅色過於接近。
- 「這個密碼太常見」及「密碼與電子郵件太相近」缺乏處理方向。
- 使用者誤以為密碼必須含特殊符號或英文字，但畫面未明確說明。

#### 建議處理

- 建立全站一致的錯誤狀態樣式。
- 錯誤文字使用符合對比標準的紅色。
- 輸入框同時顯示紅框及欄位下方的錯誤原因。
- 在密碼欄位旁列出實際規則，不要加入程式未要求的規則。
- 將 Django 原始驗證訊息改寫成可操作的雙語說明。

#### 驗收方式

- 空白、兩次密碼不同、全數字、常見密碼、過短密碼及與個人資料過度相似時，都能看到明確且一致的錯誤訊息。
- 錯誤訊息不能只依靠顏色表達。

### P1-03：密碼及安全問題答案缺少顯示／隱藏控制

測試者希望確認自己輸入的內容，並有人誤以為安全問題不能使用中文。

目前安全問題答案欄位技術上接受中文，但使用密碼欄位遮蔽內容。這是認知與操作問題，不是中文輸入功能缺失。

#### 建議處理

- 為密碼及三個安全問題答案增加個別或一致的「顯示／隱藏」按鈕。
- 預設仍維持隱藏，避免共用電腦旁觀者看到答案。
- 不要把安全問題答案回填進 HTML、網址、日誌或一般快取。

### P2-01：返回修改後，註冊資料需要重新輸入

測試者在學號確認頁返回修改時，希望保留原本填寫的內容。

#### 風險與原則

一般欄位可以從短期註冊草稿或 Session 還原。密碼不可出現在網址、HTML 原始碼、日誌或長期資料中。若要保留密碼，必須沿用既有短期草稿機制並確認安全性。

### P2-02：側欄、按鈕及可編輯區域辨識度不足

回覆包括：

- 左側功能區文字偏小。
- 私訊頁的「查看資料」按鈕偏小。
- 個人資料頁的可編輯欄位不夠明顯。

#### 建議處理

- 側欄功能文字至少維持 16px，並檢查 100% 與 125% 縮放。
- 主要觸控按鈕高度至少 44px。
- 可編輯區域使用一致的淡色背景、邊框或標題。
- 不可只用顏色表示「可編輯」。

### P2-03：學期課程的加號、減號容易被誤解

測試者認為加號、減號像「新增課程／刪除課程」，不是展開／收合。

#### 建議處理

- 改用向下／向上箭頭或 chevron。
- 與私訊、課程及其他可收合元件使用相同符號與互動方式。
- 加上適當的 `aria-expanded` 與可辨識標籤。

### P2-04：修改課程入口不夠直接

測試者希望不用進入課程詳細頁才找到修改功能。

#### 建議處理

不要直接在卡片堆放多個大型按鈕。可在課程卡片保留「查看課程」，另增加 `⋯` 更多操作選單，提供「修改」與「取消」。

### P2-05：確認完成狀態不夠明顯

完成「確認無誤」後，測試者建議把「目前確認結果」顯示為綠色。

#### 建議處理

統一全站狀態色：

- 綠色：已完成、已確認、有效。
- 黃色：等待處理。
- 紅色：未通過、遭拒絕、需要修正。
- 灰色：尚未開始、不適用。

## 5. 需要系辦決定的事項

以下項目不是可以直接由工程端決定的程式錯誤。

### D-01：母語選單是否新增粵語及如何排序

測試者建議加入「粵語」，並統一語言排序。

需確認：

1. 顯示名稱使用「粵語 / Cantonese」或「廣東話 / Cantonese」。
2. 依中文名稱、英文名稱排序，或常用語言置頂後再排序。
3. 新增後，註冊、個人資料編輯及候選人篩選三處必須同步。

### D-02：完整的華語教學能力認證證書是否可作為口語能力證明

目前說明指定「華語口語與表達」成績證明。測試者詢問完整證書是否也可接受。

系統目前只驗證檔案格式、內容與容量，不會自動判斷行政文件種類，最後仍由管理員審核。是否接受完整證書須由系辦決定後再修改文案。

### D-03：已核准的口語能力證明是否允許使用者自行更換

口語能力證明介面仍需支援註冊時未上傳、退回後重新送審及更換錯誤文件，不宜直接刪除。

建議依狀態顯示不同按鈕：

- 尚未上傳：上傳證明。
- 待審核：更換文件。
- 已退回：重新送審。
- 已通過：需由系辦決定是否允許直接更換；若允許，須警告會重新進入審核。

## 6. 測試流程缺口

### T-01：邀請五天到期不適合要求封測者實際等待

3 份回覆無法完成 6.5，原因是測試期間不足五天。

#### 建議

- 保留現有自動化測試驗證五天期限。
- 人工封測由管理員建立一筆即將到期的邀請，只驗證到期後的畫面與操作限制。
- 不應讓測試者等待五天才完成表單。

### T-02：角色未同步配合，造成後半段大量缺測

部分邀請沒有被學生接受，導致配對、私訊、排課、簽到、課堂紀錄、補登、時數及證明下載被標示為「不適用」或「等待配合角色完成」。

這些結果代表「沒有形成測試條件」，不是「功能通過」。

#### 下一輪安排

1. 每位老師指定一位學生為固定測試搭檔。
2. 約定同一時段操作邀請、接受及私訊。
3. 管理員同時在線處理口語能力與補登審核。
4. 至少一組完成「邀請 → 接受 → 配對 → 排課 → 簽到 → 雙方紀錄 → 相互確認 → 時數成立 → 證明下載」。
5. 另一組專門測試拒絕、退回、取消、逾時及錯誤流程。

### T-03：手機與其他瀏覽器覆蓋不足

所有回覆都以電腦為主要裝置，瀏覽器只有 Chrome 與 Safari。本次不能證明手機實機版與 Windows 環境穩定。

至少補測：

- iPhone Safari。
- Android Chrome。
- Windows Chrome 或 Edge。
- macOS Safari 或 Chrome。

### T-04：有一個測試結果空白，但表單仍可提交

其中一份回覆的 13.2 沒有答案，但仍完成送出前確認。

#### 建議檢查

- Google 表單的每個「測試結果」是否均設為必填。
- 該回覆是否在題目改成必填前就已提交。
- 送出前確認是否只是一個勾選題，沒有真正檢查所有結果。

### T-05：Excel 驗收狀態公式顯示 `#REF!`

下載後的 Excel 中，所有「驗收狀態」均為 `#REF!`。原始回答仍存在，但不能直接篩選待補測或已完成。

目前的陣列公式範圍彼此重疊，不適合這份匯出檔。建議改用逐列公式，例如第二列：

```excel
=IF(A2="","",IF(COUNTIF(B2:FU2,"*等待配合角色完成*")>0,"待補測","已完成"))
```

再向下填滿。若公式由 Apps Script 建立，應修正產生公式的程式，而不是每次匯出後人工處理。

## 7. 建議執行順序

1. 修正超大口語能力文件上傳卡住及 413 錯誤處理。
2. 修正錯誤訊息樣式與密碼規則說明。
3. 修正 Excel 驗收狀態公式及 Google 表單漏填問題。
4. 安排老師、學生、管理員同步完成跨角色補測。
5. 補做手機實機與 Windows 瀏覽器測試。
6. 統一側欄、按鈕、編輯區、收合符號及狀態色。
7. 等系辦確認粵語名稱、口語能力證明文件範圍及核准後能否更換文件。

## 8. 完成條件

本輪修正不能只以單元測試通過作為結案條件。至少要同時滿足：

- Django 完整測試全數通過。
- 正式 VM 能正確拒絕 1 MB 以上的口語能力文件並顯示清楚訊息。
- 原本核准文件不會被失敗上傳覆蓋。
- Chrome、Safari、iPhone Safari、Android Chrome 至少各完成一次核心流程。
- 至少兩組老師／學生完成跨角色端到端流程。
- Google 表單不再有漏填結果。
- Excel 匯出後「驗收狀態」不再顯示 `#REF!`。
- 所有行政規則變更均先取得系辦確認，再修改程式與文件。
