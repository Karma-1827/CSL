# MPTS 封閉測試：開發與維運驗收計畫

本文件用於正式網址 `https://mpts.tcsl.ntnu.edu.tw/` 的封閉測試（封測）。目標是在邀請實際使用者前，確認三種角色、跨角色流程、行政作業及手機介面均能正常完成。

> 封測不是壓力測試。封測期間僅使用少量、標示清楚的測試帳號與測試資料；不可匯入真實全系名冊、建立真實證明，或用大量自動請求測試正式站。

## 1. 封測目標與完成標準

本輪確認：

- 使用者可以依名冊身分完成註冊、登入、帳號恢復與個人資料建立。
- Tutor、一般外籍生 Tutee、馬里蘭 Tutee 與 Admin 各自只看得到應有的功能與資料。
- 配對、解除、排課、簽到、課堂紀錄、互認、補登、通報、私訊、時數及證明下載的資料流程正確。
- Admin 可以完成名冊、資格、配對、課程、補登、通報、學期、時數與匯出的行政工作。
- 桌機與手機瀏覽器的主要頁面可正常操作；畫面不出現 500 錯誤、敏感資料錯置或明顯版面問題。

封測完成的最低標準：

1. P0（無法登入、越權看到資料、資料遺失、錯算時數、錯誤產生證明、500 錯誤）為 0 件。
2. 每一項「必測」案例皆有通過、明確不適用或已記錄的問題。
3. P1（主要流程卡住、行動版無法操作、Admin 無法完成行政作業）須完成修正或有系辦確認的暫行處理方式。
4. 封測資料、帳號與產生的證明已列入清理清單；不得誤留為正式行政紀錄。

## 2. 測試前準備

### 2.1 角色對照與帳號附件

所有帳號、姓名、Email、課程主題及佐證連結均使用測試資料；內容請標示「封測」，避免與真實行政資料混淆。

完整的 23 筆封測名冊、角色、身份別、計畫、建議搭配及特殊測試情境，統一放在附件：[CLOSED_BETA_TEST_ACCOUNTS.md](CLOSED_BETA_TEST_ACCOUNTS.md)。其中馬里蘭計畫配置 4 位 Tutor 與 7 位 Tutee，用來驗證一般配對及 Admin 手動配對。測試密碼不可記錄在本文件或群組訊息，應由管理員以安全方式分派。

本計畫中的 `A1`、`T1`、`S1`、`M1` 等為案例代號；請依附件找到實際分派帳號。開始前，Admin 應確認名冊的角色、身份別與所屬計畫正確。尚未註冊的 Tutor 學制顯示「不適用」屬正常狀態，會在個人資料建立時由使用者選擇並更新。

### 2.2 測試資料

- 至少 1 份可上傳的口語能力證明檔（合法 PDF、JPG 或 PNG，且小於 1 MB）。
- 1 份不合法檔案（錯誤副檔名、超過大小或非圖片內容），用來確認上傳被拒絕。
- 1–5 個可公開檢視的課堂佐證連結；連結內容限測試素材，勿放學生個資。
- 至少 2 個測試學期：一個目前進行中、一個已結束；必要時建立未來學期。
- 至少 3 堂測試課：即將上課、已結束待補登、已完整確認且有效成立。
- 封測前確認 PostgreSQL、`media/` 與 NFS 備份已成功執行一次，並記錄備份時間。

### 2.3 測試環境規則

- 使用正式網址與正式 HTTPS，不使用 `localhost`。
- 若測試需要重複註冊，請由 Admin 先清理特定測試名冊與測試帳號；不得刪除真實資料。
- 測試課程、私訊、通報及佐證連結均在內容開頭加上 `【封測】`。
- 先不要對正式網站執行自動化大量登入、爬蟲、壓力測試或弱點掃描；這些另依維運與資訊中心流程排程。

## 3. 測試執行順序

建議照以下順序進行。前一階段出現 P0/P1 問題時，先記錄與修正，再繼續後續流程。

```text
Admin 確認已匯入測試名冊／設定學期
→ 使用者註冊與登入
→ 建立個人資料與資格審核
→ 候選人瀏覽、邀請與配對
→ 課表、簽到、課堂紀錄、互認
→ 補登、通報、解除配對
→ 私訊、時數、證明下載
→ Admin 總覽、匯出、稽核與清理
```

## 5. 手機與瀏覽器抽查

使用至少一台 iPhone 或 Android 手機，以及一台桌機瀏覽器。下列頁面每種角色至少抽查一次：

- 登入、註冊、帳號恢復。
- Tutor／Tutee Dashboard、側欄、帳號選單。
- 尋找配對、邀請與配對資料卡片。
- 課表、課堂明細、簽到、課堂紀錄及佐證連結。
- 私訊、時數、證明下載。
- Admin 核心面板與名冊篩選。

每一頁確認：文字不重疊、按鈕可點、表單可輸入、長文字可換行、沒有水平捲動造成主要操作被遮住。

## 6. 問題回報格式

每個問題建立一筆紀錄。截圖不得包含密碼、安全問題答案、真實學號、真實 Email 或其他不必要個資。

| 欄位 | 填寫內容 |
| --- | --- |
| 問題編號 | 例如 `BETA-001` |
| 嚴重度 | P0／P1／P2／P3 |
| 測試案例 | 例如 `CL-07` |
| 帳號角色 | Admin／Tutor／Tutee／Maryland Tutee |
| 裝置與瀏覽器 | 例如 iPhone Safari、Mac Chrome |
| 操作步驟 | 可重現的逐步操作 |
| 預期結果 | 依本文件或已確認規則 |
| 實際結果 | 畫面、提示或錯誤內容 |
| 截圖／時間 | 遮蔽敏感資料後的畫面與發生時間 |
| 補充資料 | 對象、學期、測試課程代號，不放密碼 |

嚴重度定義：

- **P0**：無法登入、500 錯誤、資料／權限外洩、遺失資料、錯誤計算或核發正式時數。
- **P1**：主要流程無法完成、Admin 無法處理行政工作、手機無法操作。
- **P2**：有替代方式可完成，但流程、提示或顯示錯誤。
- **P3**：文字、翻譯、間距、色彩或其他不影響功能的 UI 問題。

## 8. 封測後才進行的壓力測試

壓力測試另行規劃，不在此封測文件直接執行。正式站壓測前至少須具備：

- 使用測試帳號與不含真實個資的測試資料。
- CPU、RAM、磁碟、PostgreSQL、Nginx、Gunicorn、HTTP 5xx 與備份失敗監控。
- 可即時停止測試的維運者與離峰時段。
- 漸進流量：先 20、50、100 位模擬使用者，再依監控結果決定是否提高。
- 已確認不會測到登入節流、帳號恢復、檔案上傳或其他容易造成資料污染／鎖定的端點。
- 完整備份與明確還原方案。

壓測完成後應記錄同時使用者數、每秒請求數、平均／P95 回應時間、錯誤率、CPU、RAM、DB 連線數與發現的瓶頸，作為資訊中心弱點掃描及正式公開前的維運依據。
